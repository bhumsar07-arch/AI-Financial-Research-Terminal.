1. System Overview

The AI Financial Research Terminal uses Retrieval-Augmented Generation (RAG) to answer analyst questions about companies. Instead of relying on an LLM's training data (which is outdated and prone to hallucination for specific company filings), the system grounds every answer in actual ingested documents.

💡
Why RAG instead of pure LLM?
A language model like Gemini was trained on data up to a cutoff date. It cannot know ITC's Q4 FY25 exact revenue, what the CFO said on a specific earnings call, or a particular balance sheet line item. RAG solves this by finding the actual document excerpt and giving it to the LLM as context — the LLM then reasons over real evidence, not memory.

Three document types are supported:

Document TypeSourceParser PathSpecial Handling
Annual Reports PDF upload pdfplumber → pypdf fallback Table structure preservation
Quarterly Results / Investor Presentations PDF upload pdfplumber → pypdf fallback Slide-by-slide chunking
Earnings Call Transcripts .txt file TranscriptParser (regex) Speaker detection, Q&A section tagging

3.2 The Broken Embedder Explained

# v1.0 embedder — the core problem
for i, word in enumerate(words):
    # MD5 hash of word → maps to a bucket in 384 dimensions
    h = int(hashlib.md5(word.encode()).hexdigest(), 16)
    idx = h % self.dimension
    vector[idx] += 1.0
    
    # Bigram: word pair gets extra weight
    if i > 0:
        bigram = f"{words[i-1]}_{word}"
        bh = int(hashlib.sha256(bigram.encode()).hexdigest(), 16)
        vector[bh % 384] += 1.5

# L2 normalize
vector = vector / np.linalg.norm(vector)

This is essentially a bag-of-words with character hashing. The word "profit" is assigned to bucket #217. The word "earnings" is assigned to bucket #94. They are completely unrelated in this vector space — but in reality they mean the same thing.

4.2 Storage — pgvector

❌ v1.0 — TEXT column

"embedding" TEXT
-- "[0.023, -0.11, ...]"
-- No index
-- No native ops

✅ v3.0 — pgvector column

"embedding_v" vector(384)
-- Native type
-- ivfflat ANN index
-- <=> cosine operator
-- v3.0 retrieval — entire similarity search in PostgreSQL
SELECT content, speaker_name, document_title,
       1 - (embedding_v <=> %s::vector) AS similarity
FROM document_chunks
WHERE company_id = %s AND embedding_v IS NOT NULL
ORDER BY embedding_v <=> %s::vector
LIMIT 20;  -- 4x for re-ranking headroom

File: rag-service/app/ingestion/chunker.py

Unchanged from v1.0 — adequate design retained:

  • Splits on \n\n paragraph boundaries first (preserves semantic units)
  • Then falls back to word-count splitting if a paragraph exceeds the target
  • 60-token overlap between adjacent chunks prevents boundary information loss
  • Stores page_number, speaker_name, speaker_role, is_management, section per chunk

5.5 Casual Query Router (NEW in v3.0)

A lightweight regex filter runs before vector search. If the query matches a casual pattern (hi, thanks, how are you, etc.), a natural conversational response is returned directly — zero DB round-trips.

→ Full vector search runs
→ 0 relevant chunks found
→ "I couldn't find relevant information"

✅ v3.0

User types "hi"
→ is_casual_query() → True
→ "Hey! I'm your AI financial analyst..."
→ No DB hit, instant response

6. Why Each Change Was Made

Change 1: sentence-transformers Embedder

✅
Biggest impact, first priority. This single change fixes the fundamental reason the system was returning irrelevant evidence — and therefore giving poor AI answers.

The hash-based embedder had no semantic understanding whatsoever. Two phrases meaning the same thing had near-zero cosine similarity. The sentence-transformer model was pre-trained on over 1 billion text pairs and understands financial domain language, synonyms, and paraphrasing.

Why all-MiniLM-L6-v2 specifically: It's the industry-standard small RAG embedding model — 22MB, 8ms CPU inference, 384 dimensions (same as existing schema), fully offline, no API key, MIT licensed. Larger models like all-mpnet-base-v2 (420MB) offer marginally better quality but 10x the size/latency.

Change 2: pdfplumber for PDF Parsing

Financial PDFs are table-heavy by nature. Annual reports, quarterly results, investor presentations — all contain income statements, balance sheets, segment-wise revenue breakdowns in tabular form.

pypdf.extract_text() linearises tables — it reads text in the order it appears in the PDF's internal stream, which is almost never left-to-right, top-to-bottom for multi-column tables. pdfplumber uses bounding boxes and character positions to reconstruct table structure.

Change 3: pgvector Native Storage

The TEXT column had no index. PostgreSQL's query planner couldn't help — every query required a full sequential scan. The Python brute-force code then had to: fetch all rows, deserialize each JSON string, and compute numpy dot products in a loop.

pgvector's ivfflat index clusters vectors into Voronoi cells and only searches the nearest cell at query time — reducing the comparison count from N to approximately N/lists (where lists ≈ sqrt(N)).

Change 4: Fixed Gemini Model Names

The original code used "gemini-3.6-flash" and "gemini-flash-latest" — both of which do not exist in the Google AI API. Every call raised a 404 error, which was silently caught and treated as a fallback signal. The system would fall through all candidates, then fall back to local synthesis — even with a valid API key configured.

Fixed to use real model names: gemini-2.5-flash, gemini-2.0-flash, gemini-1.5-flash, gemini-1.5-pro.
